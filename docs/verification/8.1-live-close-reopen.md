# §8.1 — Live verification runbook: Planner "close/reopen the exact session URL"

**Status:** NOT performed. This document exists so the operator can execute and record the
live check; no code path in this repository may claim live close/reopen is proven until
these steps are run against a real CDP browser and the evidence is attached.

Unit-level evidence already in place (`tests/recovery.chatgpt.test.ts`, 12 tests green):
- `recoverChatGPT` issues the exact `conversationUrl` of the configured Planner through the
  adapter's refresh path and lets the post-refresh probe decide success/failure.
- A failing refresh does not itself count as recovery; the probe does.
- Externally owned browsers are never relaunched; managed browsers relaunch at most once.

What unit tests cannot prove: that a real Chrome tab over CDP actually performs the
navigation, that the conversation renders afterwards, or that the next relay turn delivers.

## Preconditions

1. Chrome/Chromium launched with `--remote-debugging-port=9222` and signed into `chatgpt.com`
   in the profile Agent attaches to.
2. A pair configured with that `cdpUrl` and a real Planner conversation URL.
3. `npm run desktop:dev` running (or the headless service).
4. Logs open: `logs/` (supervisor.ndjson / relay) and the app's Source → Ground Truth panel.

## Steps

1. Stop the pair. Confirm the Planner conversation opens in the attached browser.
2. Manually **close the Planner tab** (or navigate it away to `about:blank`).
3. Start the pair (or trigger a planner probe cycle) and watch the logs.
4. Expected, in order:
   - Probes mark the Planner unhealthy (`conversationReachable=false`).
   - Recovery invokes the refresh path; the attached browser is steered **back to the exact
     `conversationUrl`** (no new tab if the existing one can be navigated; no other site is
     visited).
   - A fresh probe marks the Planner healthy; recovery reports
     `recovered: true, action: "reopen-conversation"`.
   - If the conversation cannot be reopened (auth wall, layout change, rate limit), the
     outcome is `INTERVENTION_REQUIRED`-class — never a silent "recovered".
5. Record: date/time, pair id, URL before/after, probe outcomes before/after, the
   supervisor log lines containing `reopen-conversation`, and whether the next relay turn
   completed. Attach screenshots of the browser tab before and after.

## Pass criteria

- The exact configured `conversationUrl` was navigated to (not a redirected conversation).
- Recovery outcome was derived from the post-action probe, not from the action itself.
- Intervention (when applicable) surfaced visibly and delivery remained blocked.

## On failure or ambiguity

- Keep the tracker entry at `~`. Do not weaken probes to make the check pass.
- Note the failure mode in `docs/v1.1-alignment-tracker.md` §8.1 verbatim.
