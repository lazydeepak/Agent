## 3. Key Functions / Exports (brief explanation added / verified)

Because "all functions" is large, below are the major exported functions and what they do, with references to the files already commented.

### CLI / Entry
- `cli.ts` — parses `cli-args`, selects adapter (`LiveOpenCodeAdapter` / `FakeOpenCodeAdapter`), calls runtime start or desktop service start.

### Adapters (`adapters/opencode/index.ts`)
- `LiveOpenCodeAdapter`, `FakeOpenCodeAdapter` — concrete adapter implementations.
- `OpenCodeSessionManager`, `OpenCodeEventSource` — interfaces for session control and event streams.
- Readiness / event-source helpers.

### Relay (`relay/index.ts`)
- `canonicalRelayIdentity()` — deterministic relay identity.
- `RelayStore`, `relay` exports — identity, verification, ledger persistence.
- `chatgpt-gate` — filters / gates ChatGPT-side interactions.
- `verifier` — validates relay state.

### Persistence (`persistence/index.ts`)
- SQLite store initialization, record write/read, persistence of session/ledger data.

### Supervisor (`supervisor/*.ts`)
- `supervisor.ts` — per-pair async supervisor loop (observation + backoff).
- `observation.ts` — event correlation, session tracking.

### Recovery (`recovery/*.ts`)
- `engine.ts` — bounded recovery: reconnect, verify session, deterministic backoff (never uses AI judgment).
- `opencode.ts` — OpenCode-specific recovery adapter.

### Validation (`validator/*.ts`)
- `readiness.ts` — pair readiness reports.
- Status classification (deterministic, not model-based).

### Runtime (`runtime/*.ts`)
- `pair-runtime.ts` — concurrent multi-pair runtime orchestration (strict isolation per pair, FIFO browser locking, no cross-pair stall).
- `adapters.ts` — adapter registry / factory.

### Application Services (`application/*.ts`)
- `control-plane-adapter.ts` — adapter bridge for worker/planner pairs.
- `desktop-service.ts` — Electron desktop integration (renderer never touches SQLite / filesystem directly; IPC via narrow `desktop:*` channel set).
- `project-pair-service.ts` — identity / ownership layer (stable ids, unique ownership, neutral `worker` / `planner` keys).
- `worker-*` services — transcript, session, progress tracking.

### Utilities (`util/*.ts`)
- `canonical.ts` — URL / identity canonicalization, hash helpers.
- `async.ts` — timeout, retry, bounded backoff primitives.
- `readiness.ts` (util) — readiness constructors.

## 4. Code index — built

Every header includes the marker:

```
* NEXT: build code index (upcoming phase — index symbols / files / functions for faster lookup).
```

That phase is now **complete**. The deterministic generator
([`scripts/generate-code-index.mjs`](../scripts/generate-code-index.mjs), run via `npm run index:code`)
scans every `src/**/*.ts` module and emits:

- [`docs/code-index.md`](./code-index.md) — a file map plus a symbol index (every exported
  function, class, interface, type, const, and re-export, with source line and signature).
- [`docs/code-index.json`](./code-index.json) — the same data, structured.

The generator derives everything from source text (no AI, no network, no unstable compiler API),
so the index is reproducible and can be regenerated after any change.

> The per-file `NEXT: build code index` header note is now historical.

## 5. How to add more comments / keep them updated

- Module-level: edit the header block at the top of each `.ts` file (same pattern for all 87 files).
- Function-level: add `// <function purpose>` or JSDoc above exported functions; the batch script only added module headers, so function-level docs can be added per-module as needed.
- Scripts: same `/** Agent-relay script — ... NEXT: build code index. */` pattern.
- Master index: update this file (`docs/module-index.md`) when modules change.
