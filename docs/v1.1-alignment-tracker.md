## §3 Message identity / durable admission / evidence
- §3.1 visible Relay ID + UTC watermark on every outbound relay message — ✓ (`src/util/watermark.ts`, all relay sends).
- §3.2 durable admission BEFORE send; crash ⇒ operation uncertain — ✓ (ledger `DELIVERING` before external send; crash ⇒ resend blocked, `AMBIGUOUS`).
  Evidence gaps closed this wave: schema v15 adds `relay_records.generation` (attempt generation, increments with every delivery attempt) and `relay_records.authorization` (what authorized the admission: `automation` for managed dispatch, `operator` for the operator-continue path). The operator-initiated "continue with fallback model" send — previously the one external send without durable admission — now goes through the same ledger fence (`DELIVERING` → `DELIVERED`/held) with `authorization="operator"`. Startup activation (§4) remains recorded in its own `startup_operations` table by design.
- §3.3 causally linked attempt/delivery facts — ~ (`attempt_count`, `verify_attempt_count`, `relay_cycles`, `generation` exist; in the current no-blind-resend design `generation` tracks `attempt_count` 1:1 (documented, deliberate); planner-delivery trace via cycle + ledger).
- §3.4 no exactly-once guarantee; no blind resend — ✓ enforced via `DELIVERING` + durable ledger + `RELAY_AMBIGUOUS` block.
- §3.5 verify by identity/history; 2-minute retry; escalate after 3 failures; never resend blindly — ✓ (`verifier.ts`, supervisor gating, `RELAY_VERIFY_MAX_ATTEMPTS`).
- §3.6 unknown remains unknown; preserve unresolved evidence — ✓ (unresolved ⇒ `DELIVERING` retained; escalation holds for operator).

## §4 Narrow startup/resume exception
- ~ Implemented with documented limits:
  - §4.2 durable startup-operation identity — ✓ `startup_operations` table (schema v14), binds exact planner/worker sessions and `mode` ('fresh'|'resume'), with durable pre-send record and configurable attempt budget (default 3).
  - §4.3 destination verifier — only attributable Planner responses (message newer than the activation op) are admitted; non-attributable ⇒ held.
  - §4.4 atomic acceptance fence — first attributable response wins via `UPDATE ... WHERE accepted_response_id IS NULL`; subsequent acceptance refused; acceptance recorded before dispatch.
  - §4.5 hold state never silently retries; `hold` is distinct from `pending`/`stabilized` and blocks dispatch; operator release via normal resume.
  - Gaps: no explicit startup-operation identity threading beyond `universal-kickoff` message ids; accepted response attribution relies on adapter-provided `createdAt`; no full live-ChatGPT verification performed; startup exception only wired into `seedPlanner` (the only managed activation path currently), not into generic pair start.

- §5.5 Unverified termination preserved + not reported as proof; prohibits conflicting dispatch until reconciled — ~ (Stop All now persists `incidentDisposition: terminated_unverified` for every pair; the recovery dashboard shows an `UNVERIFIED TERMINATION` chip on the Stop All row; reconcile path = ordinary delivery verification; no dedicated termination-verification UI beyond that).
- §5.6 Stop/Stop All overridable only by operator Start; safety holds respected — ✓ (auto-resume disabled; recovery doesn't revive stopped pairs).

## §11 Incidents, limits, permissions
- §11.2–11.3 incident budgets — ✓ attempt semantics correct (corrective attempts only; passive inspection does not count). 3-attempt budget and 10-minute window both enforced with `RECOVERY_SUSPENDED` + operator-only release.
  Ordering (§11.1): the recovery dashboard now renders Queued oldest-first with critical-first rank (INTERVENTION_REQUIRED/SUSPENDED/STOP_ALL rank first). Cross-pair engine-level sequencing does not exist — Incidents are processed inline in per-pair supervisor loops; a shared FIFO would violate the per-pair isolation boundary and is not mandated by the contract; it remains a documented gap.
  Repeated matching failures (§11.4): implemented. `RecoveryEngine.writeMetadata` normalizes each failure (`code | reason`, digits → `#`, pair id stripped, 120-char cap) and counts identical matches within the 10-minute window; ≥ 2 identical failures suspend automated recovery with `RECOVERY_SUSPENDED` (`details.action = "identical-failure-signature"`), persisted (`identical_failure_count`, `last_failure_signature`, `identical_failure_first_at`) and cleared only by operator release or a distinct failure.
- §11.4 operator-only release — ✓ `desktop:recovery:release-suspension` (operator click only) resets counter and suspension marker; recovery does NOT auto-resume on release (the next cycle observes normally).
- §11.5–11.7 permission scoping/queue release — ~ partial. Incident dispositions now persist on `supervisor_state.incident_disposition` (`resolved|awaiting_operator|held|terminated_unverified`, set by engine suspension paths and Stop All); append-only audit history exists (supervisor.ndjson). Per-project permission grants/revocation NOT implemented (no permission system exists — a genuine gap); revocation blocking new admission is only available via existing pair Stop/Pause. Stop All sets `terminated_unverified` for every pair (never claims every Worker stopped).
