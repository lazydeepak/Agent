## §4 Narrow startup/resume exception
- ~ Implemented with documented limits:
  - §4.2 durable startup-operation identity — ✓ `startup_operations` table (schema v14), binds exact planner/worker sessions and `mode` ('fresh'|'resume'), with durable pre-send record and configurable attempt budget (default 3).
  - §4.3 destination verifier — only attributable Planner responses (message newer than the activation op) are admitted; non-attributable ⇒ held.

## §7 Capture-first Start/Resume; busy-session handling
- ~ Implemented with documented limits: Start arms capture on both peers and records the boundary (START_CAPTURE_BOUNDARY event, `pair_state.last_capture_boundary_at`); §7.3/§7.4 both-busy → the operator selects the starting side (IPC `desktop:pair:select-starting-side`, "Awaiting Starting-Side Selection" UI in the pair card) and the selected side's first admission clears the selection; §7.2 event capture is bounded — 3 resubscribe attempts with the replay cursor (`pair_runtime.consumeWorkerEvents`), then an explicit UNRECOVERABLE_GAPS marker (completeness UNKNOWN, never assumed complete). Limits: no provider cursor/replay from the OpenCode SSE API itself (replay is approximated by seq-after resubscribe); gaps are marked but message-level bounded buffering beyond the replay cursor does not exist; capture alone does not block dispatch until evidence arrives (dispatch holds on NOT_READY instead).
- §7.5 Fresh Start / Resume — ✓ implemented: Fresh Start (from-trigger) sends UNIVERSAL_PLANNER_PROMPT v2 (2026-11-18), which establishes an explicit new baseline and forbids replaying/relying on prior worker instructions; the digest pinned in planner-prompt-version.test.ts. Resume for pairs with relay history passes priming "resume": direct continuation is sent ONLY when the durable ledger records no uncertainty (no DELIVERING records, no open startup operation, no UNRECOVERABLE_GAPS marker, latest cycle DELIVERED with worker completion, no FAILED worker→planner reports, no unverified-termination/held/awaiting disposition); otherwise a checkpoint briefing is sent (mode="resume" startup operation, `RESUME_BRIEFING_SENT` event) listing last known state, the latest recorded worker report marked POSSIBLE PRIOR DELIVERY, and the specific uncertainties, then requests the next job. Exact evidence semantics: `src/application/continuation-briefing.ts`; covered by `tests/continuation-briefing.test.ts` (15 tests). Limits: "proven" means "no recorded uncertainty in durable state" — adapters cannot read the live Planner conversation, so consistency is never claimed beyond ledger evidence; resume does not lock or fence the worker session beyond the startup operation.

## §11 Incidents, limits, permissions
- §11.2–11.3 incident budgets — ✓ attempt semantics correct (corrective attempts only; passive inspection does not count). 3-attempt budget and 10-minute window both enforced with `RECOVERY_SUSPENDED` + operator-only release.
  Ordering (§11.1): the recovery dashboard now renders Queued oldest-first with critical-first rank (INTERVENTION_REQUIRED/SUSPENDED/STOP_ALL rank first). Cross-pair engine-level sequencing does not exist — Incidents are processed inline in per-pair supervisor loops; a shared FIFO would violate the per-pair isolation boundary and is not mandated by the contract; it remains a documented gap.
  Repeated matching failures (§11.4): implemented. `RecoveryEngine.writeMetadata` normalizes each failure (`code | reason`, digits → `#`, pair id stripped, 120-char cap) and counts identical matches within the 10-minute window; ≥ 2 identical failures suspend automated recovery with `RECOVERY_SUSPENDED` (`details.action = "identical-failure-signature"`), persisted (`identical_failure_count`, `last_failure_signature`, `identical_failure_first_at`) and cleared only by operator release or a distinct failure.
- §11.4 operator-only release — ✓ `desktop:recovery:release-suspension` (operator click only) resets counter and suspension marker; recovery does NOT auto-resume on release (the next cycle observes normally).
- §11.5–11.7 permission scoping/queue release — ~ partial. Incident dispositions now persist on `supervisor_state.incident_disposition` (`resolved|awaiting_operator|held|terminated_unverified`, set by engine suspension paths and Stop All); append-only audit history exists (supervisor.ndjson). Stop All sets `terminated_unverified` for every pair (never claims every Worker stopped). Per-project permission system — ✓ implemented this wave (`permission_grants`, schema v17): project-scoped preferred (falls back to pair scope); actions are a closed set (currently only `model-switch-outside-approved`); modes `one-time` (consumed atomically after the authorized action succeeds) and `permanent`; revocation is an operator action that takes effect at the next admission check (immediate — no caching layer); every grant/revoke/consume is audit-logged to the append-only event log (PERMISSION_GRANTED/REVOKED/CONSUMED; revoke of an already-revoked grant logs PERMISSION_REVOKE_NOOP). Enforced at the one real in-process elevation in this stack: out-of-approved-list `switchWorkerModel` (previously a hard rejection, now grant-authorized). UI: Settings → Permissions card (list/grant/revoke; preview bridge SIMULATED mirror; IPC `desktop:permission:{list,grant,revoke}`). Tests: `tests/permission-service.test.ts` (16). Limits (honest): no in-process executor exists for agent-requested runtime repairs, so there is nothing yet to gate beyond the model switch; shared-service restart remains governed by the `safe` policy + verified-idle gate, NOT by grants; base relay authority remains pair Stop/Pause (unchanged by design). Queue/stale indicators (§11.6) and multi-action permission surface remain open.
